# `rssmlite` — Project Specification

> **Naming note:** this project was originally specified under the name
> `worldmodel`. PyPI rejected that name on upload — its similarity filter
> flagged it as too close to the existing `worldmodels` (plural) package.
> Renamed to `rssmlite` before any code was written (still within P0).
> All references below use the final name; the roadmap/commit history
> documents the actual rename if you want the play-by-play.

**Author:** Min Htet Myet ([github.com/Mattral](https://github.com/Mattral))
**Status:** Draft v1.0
**Type:** Independent open-source project (not affiliated with any institution)
**Last updated:** 2026-08-28

---

## 1. One-Line Summary

`rssmlite` is a lightweight, well-documented, PyTorch-only library for learning
RSSM-based (Recurrent State-Space Model) world models — in the DreamerV2/V3
tradition — on Gymnasium environments, designed to run end-to-end on a free
Google Colab T4 GPU with zero external datasets.

---

## 2. Background & Motivation

World models let an agent learn a compact internal simulation of its environment,
then train a policy entirely inside that simulation ("imagination") instead of
needing millions of real environment interactions. The reference lineage is:

- Ha & Schmidhuber (2018) — original "World Models" paper
- Hafner et al. (2019) — PlaNet, introduces the RSSM
- Hafner et al. (2020/2021/2023) — DreamerV1/V2/V3

Existing implementations are either:
- Full research codebases (official DreamerV3 repo) — powerful but heavy,
  JAX-based, not approachable for someone who wants to read and extend the code.
- Massive general-purpose RL frameworks (TorchRL, etc.) — comprehensive but
  not focused on world models as the primary object of study.

**The gap:** there is no minimal, PyTorch-native, Colab-friendly, pedagogically
clear world model library aimed at people who want to *understand and extend*
an RSSM, not just call a black-box `.fit()`.

`rssmlite` fills that gap.

---

## 3. Goals

1. Provide a clean, importable PyTorch implementation of an RSSM-based world
   model (`pip install rssmlite`).
2. Support a small set of well-understood Gymnasium environments out of the box:
   CartPole, Acrobot, Pendulum, LunarLander.
3. Make the internal mechanics inspectable and visualizable: latent space
   plots, imagined vs. real rollout comparisons, reconstruction quality.
4. Be runnable entirely on a free Google Colab T4 GPU, with no external
   datasets — all training data is generated by the agent interacting with
   the environment.
5. Be genuinely well documented: architecture docs, API reference, runnable
   notebooks that map 1:1 to documented experiments.
6. Serve as a credible foundation for an independent research
   contribution (e.g. an ablation study or architecture variant) that could
   later be written up and shared (arXiv / workshop paper), without requiring
   institutional affiliation.

## 4. Non-Goals

- **No robotics / physical embodiment.** No ROS, no simulators like MuJoCo
  requiring physical robot bodies, no sim-to-real transfer.
- **No Linux-specific tooling or ROS dependency.** Everything must run on
  Windows, macOS, or Colab identically.
- **Not a competitor to TorchRL or Stable-Baselines3.** No attempt to be a
  general-purpose RL framework. Scope stays narrow: world models specifically.
- **Not chasing SOTA benchmarks.** The goal is clarity and correctness on a
  small set of environments, not leaderboard performance on Atari100k or
  large-scale suites.
- **No pixel-based Atari/vision-heavy environments in the initial scope**
  (state-vector environments only, to keep Colab T4 compute modest). Pixel
  support may become a later stretch goal, not a v1 requirement.

## 5. Success Criteria — What Does Success Look Like?

Success is defined in layers, from minimum viable to stretch:

**Layer 0 (must happen first):**
- [ ] The name `rssmlite` is reserved on PyPI under this project's ownership.

**Layer 1 (core library works):**
- [ ] `pip install rssmlite` installs a working package.
- [ ] A user can train an RSSM world model on CartPole in a single Colab
  notebook, end to end, in under 30 minutes on a T4.
- [ ] The world model's imagined rollouts are visually/quantitatively
  comparable to real rollouts (reconstruction + reward prediction quality
  reported, not just claimed).
- [ ] At least 3 environments (CartPole, Acrobot, LunarLander) are supported
  via config files, not code changes.

**Layer 2 (it's a real library, not a script):**
- [ ] Documented, versioned API (`RSSM`, `RSSMAgent`, `ReplayBuffer`, configs).
- [ ] Tests pass in CI on every push.
- [ ] Docs site or `docs/` folder covers architecture, quickstart, and API.
- [ ] README has "Open in Colab" badges that actually work for a first-time
  visitor with zero local setup.

**Layer 3 (it's a contribution, not just a reimplementation):**
- [ ] At least one genuine novelty artifact exists: an ablation study
  (e.g. removing stochastic latents, comparing KL balancing choices) or an
  architecture variant (e.g. Transformer-based dynamics instead of GRU),
  with results documented and reproducible.
- [ ] A short technical write-up (paper or long-form report) exists,
  summarizing the novelty artifact's findings, suitable for posting to
  arXiv or submitting to a workshop.

**Layer 4 (stretch — not required for v1 success):**
- [ ] Independent-researcher paper submission (arXiv and/or a workshop).
- [ ] External users (not you) star, fork, or open issues on the repo.

The project is considered a success once **Layer 2** is complete, even if
Layers 3–4 never happen. Layers 3–4 are the ambition, not the bar.

## 6. System Design Philosophy

These are the principles that should guide every design decision in this repo:

1. **Readable over clever.** Code should be understandable by someone who has
   read the DreamerV3 paper once. Avoid excessive abstraction, metaprogramming,
   or config-driven indirection that obscures the actual math.
2. **PyTorch only.** No JAX, no TensorFlow. One deep learning framework,
   because the target audience is people who already know PyTorch and want
   to extend this, not learn a second framework first.
3. **Config-driven experiments, code-driven architecture.** Which environment
   to run, hyperparameters, and logging should be YAML config. The actual
   model code (RSSM, encoder, decoder) should not need to change to run a
   new environment — only a new config.
4. **No hidden state, no framework magic.** Avoid Trainer-style abstractions
   that hide the training loop. A user should be able to open `train.py` and
   see the actual loop: collect data → train world model → train actor-critic
   in imagination → repeat.
5. **Colab-first, but not Colab-only.** Every notebook must run top-to-bottom
   on a free-tier Colab T4 with no manual intervention. The same code should
   also run locally without Colab-specific hacks.
6. **Notebooks are thin; the package is thick.** Notebooks import from
   `rssmlite` and call a handful of high-level functions. They do not
   contain model definitions or training loop internals — that logic lives
   in the package where it's tested and versioned.
7. **Self-contained data.** No external dataset downloads, ever. The
   environment is the data source. This keeps the project reproducible
   with zero data-hosting concerns.
8. **Document as you build, not after.** Every module gets a docstring
   before it gets a second function. Every notebook gets a one-paragraph
   "what this shows and why" cell before the first code cell.

## 7. Target Environments (v1 scope)

| Environment | Type | Why included |
|---|---|---|
| CartPole-v1 | Discrete actions, low-dim state | Fastest sanity check, ~20 min on T4 |
| Acrobot-v1 | Discrete actions, sparse reward | Tests reward-prediction under sparsity |
| Pendulum-v1 | Continuous actions | Tests continuous action head |
| LunarLander-v3 | Discrete/continuous, shaped + terminal reward | Hardest env in scope; non-Markovian reward structure is a good stress test |

All are Gymnasium-native, install via `pip install gymnasium[box2d]` for
LunarLander, no other dependency.

## 9. Package Architecture (`rssmlite/`)

**Core classes (initial public API):**

```python
from rssmlite import RSSM, RSSMAgent, ReplayBuffer
from rssmlite.backbones import GRUDynamics, TransformerDynamics
```

- `RSSM` — the world model itself: encoder, recurrent+stochastic latent,
  decoder, reward head, continue head. Backbone (GRU vs Transformer) is
  injectable, not hardcoded.
- `RSSMAgent` — wraps an `RSSM` with an actor-critic trained purely on
  imagined rollouts. Exposes `.train()`, `.imagine_rollout()`,
  `.visualize_latent_space()`.
- `ReplayBuffer` — stores sequences of `(obs, action, reward, done)` and
  samples fixed-length training sequences.
- `configs/*.yaml` — environment + hyperparameter definitions, loaded via
  `RSSMAgent.from_config(path)`.

**Design constraint:** every class above must be understandable by reading
its file top to bottom in under 10 minutes. If a class grows past that,
split it.

## 10. Notebooks

Notebooks are **thin wrappers** around the package — they exist to make
results visible and reproducible, not to hold logic.

| Notebook | Purpose |
|---|---|
| `01_world_model_intro.ipynb` | Explains the RSSM concept, trains a world model only (no policy) on CartPole, visualizes reconstruction quality. This is the "understand the idea" notebook. |
| `02_cartpole_experiment.ipynb` | Full DreamerV3-style loop: world model + actor-critic trained in imagination. Reports sample efficiency vs. a model-free baseline. |
| `03_lunarlander_experiment.ipynb` | Same as above, harder environment. Discusses the non-Markovian reward issue and how the world model handles (or fails to handle) it. |
| `04_ablation_study.ipynb` | The novelty contribution: systematically remove/swap components (stochastic latent, KL balancing, GRU→Transformer backbone) and report what breaks. This notebook's output feeds directly into `docs/ablation_study.md` and any future paper draft. |

Every notebook starts with the same Colab bootstrap cell (clone repo,
`pip install -e .`, mount Drive for checkpoints) so a first-time user can
run any notebook independently.

## 11. User Experience & Personas

**Persona A — Someone extending the code (you, primarily)**
```python
from rssmlite import RSSMAgent
import gymnasium as gym

env = gym.make("LunarLander-v3")
agent = RSSMAgent.from_config("configs/lunarlander.yaml")
agent.train(env, steps=200_000, checkpoint_dir="./ckpts")
agent.visualize_latent_space()
agent.imagine_rollout(steps=15)
```

**Persona B — A researcher wanting to swap a component**
```python
from rssmlite import RSSM
from rssmlite.backbones import TransformerDynamics

rssm = RSSM(dynamics=TransformerDynamics(d_model=256), latent_dim=32)
```

**Persona C — Someone reproducing a result from the docs/paper**
- Clicks "Open in Colab" badge in the README.
- Notebook runs top-to-bottom with no edits required.
- Output plots match what's shown in `docs/ablation_study.md`.

**Non-goals for UX:** no CLI wizard, no web dashboard, no hosted demo in v1.
The experience is: clone/pip install → import → call a small number of
well-named methods.

## 12. Compute & Data Requirements

- **Compute:** Google Colab free tier, T4 GPU (16GB VRAM). All target
  environments are state-vector (not pixel) based, so VRAM use stays low
  (well under 2GB for the model itself).
- **Data:** None external. All training data is generated by the agent
  interacting with the Gymnasium environment at training time. No datasets
  to download, host, or version.
- **Checkpointing:** Required — Colab sessions can disconnect. Every
  training script/notebook must checkpoint to Google Drive at a configurable
  interval and be resumable from the last checkpoint.

## 13. Documentation Plan (`docs/`)

Each file below should exist before v1.0 is considered "done":

- `architecture.md` — RSSM math notation, diagram, and why each design
  choice (categorical latents, KL balancing, symlog) was made.
- `getting_started.md` — install instructions (pip and from-source), first
  training run, expected output.
- `api_reference.md` — every public class/function with signature and a
  one-paragraph description.
- `colab_guide.md` — Colab-specific setup: mounting Drive, checkpoint
  resumption, avoiding disconnect data loss.
- `ablation_study.md` — the write-up of the novelty experiment; this is the
  document that would later become a paper draft.

- `publishing.md` — a running log of the PyPI/arXiv publishing process
  itself, useful for your own reference and for anyone following the same
  path as an independent researcher.

## 14. Publishing Plan

**Step 1 (do first, before any code is written): Reserve the PyPI name.**
Publish a minimal placeholder package (`rssmlite==0.0.1`) with real
metadata (description, license, GitHub link) to claim the name permanently.
This is non-negotiable as the first action — PyPI names are first-come,
first-served with no reservation mechanism other than publishing.

**Step 2:** Build the GitHub repo structure (Section 8) with a working
CartPole example. Tag this as an early `0.1.0` release once Layer 1 success
criteria (Section 5) are met.

**Step 3:** Iterate to Layer 2 (real library: tests, docs, CI). Release as
`0.2.0`+.

**Step 4:** Complete the novelty artifact (ablation study or backbone
variant) from Section 5, Layer 3.

**Step 5 (optional/stretch):** Write up findings, get an arXiv endorsement
(via GitHub repo as credibility signal, community endorsement request),
and/or submit to a NeurIPS/ICLR workshop. No institutional affiliation is
required for any of this — "Independent Researcher" is an accepted
affiliation at essentially all major venues and on arXiv.
